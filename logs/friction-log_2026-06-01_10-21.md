## Friction Points

### F1: Chained `snow stage copy` commands garbled by background-terminal line wrapping

- **Step:** 4 (Upload configs)
- **Severity:** Low
- **What happened:** Running 6 `snow stage copy` calls chained with `&&` in a single `run_in_background` bash invocation, the terminal echo wrapped long lines and mangled the 5th/6th commands (gateway + control_app specs). The `snow stage` token was lost and the CLI reported `Got unexpected extra arguments (copy ...)`. First 4 uploads (PBF, ors-config, download_map.py, downloader_spec) succeeded; last 2 failed. Final exit code was 2.
- **Resolution:** Re-ran the two affected `snow stage copy` calls individually (one command per line, no long `&&` chain). Both succeeded; `LIST @ORS_SPCS_STAGE` confirmed all 6 files present.
- **Recommendation:** In `build-images.md`/SKILL Step 4, prefer one `snow stage copy` per bash line (not a single long `&&` chain) when running in background terminals, or write each upload as its own short command. The wrapping is a terminal artifact, not a CLI bug — keeping commands short avoids it.

### F2: First image batch aborted with EXIT=127 after pushing 2 of 4 images

- **Step:** 5 (Build images)
- **Severity:** Low
- **What happened:** A single background bash chain built+pushed openrouteservice and downloader successfully (digests confirmed), then the combined script terminated early with `EXIT=127` before gateway/vroom completed. Root cause appeared to be the interleaved echo/`tail` piping in the background shell rather than a real Docker failure.
- **Resolution:** Verified the registry with `snow spcs image-repository list-images` (only 2 present), then re-ran gateway + vroom builds in a dedicated background job logging to a file (`/tmp/gw_vroom.log`). Both built and pushed cleanly (GATEWAY_PUSH_EXIT=0, VROOM_PUSH_EXIT=0). All 5 images confirmed in the repo afterward.
- **Recommendation:** Build/push each image in its own logged step (redirect to a file, then grep for the digest) rather than chaining 4 build+push pairs with inline `| tail` in one invocation. The `push refers to repository ... Waiting` carriage-return spam also makes inline monitoring unreliable — file redirection + digest grep is the robust pattern (already noted in build-images.md §4; worth promoting to the main flow).

### F3: Taxi `seed-data.sql` first `snow sql -f` run exited code 1 on VW_TRIP_SUMMARY; clean on re-run

- **Step:** 8 (Deploy demos — Fleet Taxis)
- **Severity:** Low
- **What happened:** The first `snow sql -f fleet-intelligence-taxis/references/seed-data.sql` run created the schema, CONFIG, and VW_DRIVER_LOCATIONS but exited code 1 at the VW_TRIP_SUMMARY CTE view, with no explicit SQL error in the captured output. Creating that same view directly via the SQL tool succeeded immediately.
- **Resolution:** Re-ran the (idempotent, CREATE OR REPLACE) seed file end-to-end. All 7 views created; `SHOW VIEWS` and row-count checks (TRIP_SUMMARY=5685, DRIVER_LOCATIONS_V=518535) confirmed success.
- **Recommendation:** Looks like a transient/ordering hiccup on first execution. Because the file is fully idempotent, a single automatic retry on non-zero exit would mask this. Consider adding a "re-run once on failure" note to the taxi quick-start (the route-optimization skill already documents re-running is safe).
