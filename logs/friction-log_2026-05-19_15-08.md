## Friction Points

### F1: `02_routing_functions.sql` references `REGION_CATALOG` which is only created in `03_region_management.sql`

- **Step:** 6 (Deploy app SQL modules)
- **Severity:** High (would block any first install if user runs only 02)
- **What happened:** When chaining `01_core_infra.sql` → `02_routing_functions.sql` → `03_region_management.sql` in order, module 02 emitted a SQL compilation error mid-run:
  ```
  002003 (42S02): Object 'OPENROUTESERVICE_APP.CORE.REGION_CATALOG' does not exist or not authorized.
  ```
  The functions `DIRECTIONS`, `ISOCHRONES_CLIPPED`, `REGION_FOR_POINT`, `POINT_IN_REGION`, `SAMPLE_ADDRESSES_FOR_REGION` reference `REGION_CATALOG` (lines 130, 256, 273 in 02). `REGION_CATALOG` is created at line 6 of 03. Because `snow sql -f` returns exit 0 on per-statement errors, the chain still ran 03→06 and the user only sees a partial failure if they read every line of stdout.
- **Resolution:** Re-ran `02_routing_functions.sql` after 03 had created `REGION_CATALOG`. All functions then created cleanly.
- **Recommendation:**
  1. Reorder modules so the table is created in 01 (alongside `REGION_REGISTRY`), OR
  2. Run 03 before 02, OR (cleanest)
  3. Add `CREATE TABLE IF NOT EXISTS OPENROUTESERVICE_APP.CORE.REGION_CATALOG (...)` at the top of 02 with the same DDL as 03 (idempotent), so 02 is self-sufficient.
  4. Update `SKILL.md` Step 6 to either run `02` twice or change ordering. Today's order silently leaves a few core ORS functions in an unbuildable state on a clean install.
  5. Make `snow sql -f` exit non-zero on per-statement errors (or have the skill grep stderr for `Error`) so a regression like this surfaces immediately.

### F2: `backload-matching` views return 0 rows on a default San Francisco install

- **Step:** 8 (Deploy demos)
- **Severity:** Low (page renders an empty state; non-blocking)
- **What happened:** After running `bootstrap.sql`, `VW_TRAILERS=0` and `VW_INTERNAL_VOLUMES=0`. Only `VW_EXTERNAL_OFFERS` had 300 rows (it is region-agnostic and reads `FACT_FREIGHT_OFFERS` directly).
- **Resolution:** None during this run - documented and continued. The backload demo is scoped against `vehicle_type=hgv` + `region=Germany`, but the seed data is `ebike` + `SanFrancisco`. The two trailer-side views project from `SYNTHETIC_DATASETS.UNIFIED.{DIM_FLEET, FACT_TRIPS}` filtered by the active CONFIG row, so they correctly return zero rows for a non-HGV / non-Germany preset.
- **Recommendation:**
  1. `backload-matching/SKILL.md` already lists Germany as a prerequisite, but `build-routing-solution/SKILL.md` Step 8 places Backload in the "Recommended demos" list without flagging the region/vehicle dependency. Either:
     - Move backload-matching to a separate "Requires Germany region + HGV preset" group in the demo selection table, OR
     - Have `bootstrap.sql` print a warning if the active CONFIG.VEHICLE_TYPE != 'hgv' or REGION != 'Germany' (e.g., `SELECT 'WARNING: backload-matching expects HGV/Germany; current preset returns 0 trailers' WHERE ...`).
  2. The skill mentions an optional one-time backfill (`backfill-freight-offers.sql`) - confirm the seed parquet (`datasets/...FACT_FREIGHT_OFFERS`) covers all regions, otherwise greenfield SF installs already have offers but new-region installs may need the backfill.
