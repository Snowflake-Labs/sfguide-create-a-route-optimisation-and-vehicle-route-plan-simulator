## Friction Points

### F1: `snowflake-scripting-guidelines.md` version table drifted from `image-versions.env` (BLOCKER)

- **Step:** 3 (engine provisioning pre-flight, `check_image_versions.sh`)
- **Severity:** High
- **What happened:** `image-versions.env` declared `DOWNLOADER_TAG=v0.0.7` but the version table in `references/snowflake-scripting-guidelines.md` still listed `downloader v0.0.6`. The pre-flight `check_image_versions.sh` failed with `MISMATCH: snowflake-scripting-guidelines.md missing downloader:v0.0.7` and aborted engine provisioning.
- **Resolution:** Bumped the table cell to `v0.0.7`. Commit `6d15a08`.
- **Recommendation:** The version table is hand-maintained and drifts silently. Either generate that table from `image-versions.env` at doc-build time, or add a pre-commit hook assertion (the repo already has `.githooks/pre-commit` that could run `check_image_versions.sh`).

### F2: route_optimization pack - `FLEET_VEHICLE_PROFILE` entity generated the wrong view name (BLOCKER)

- **Step:** 4 (packs)
- **Severity:** High
- **What happened:** data-model.yaml entity was named `FLEET_HGV_PROFILE` (generating `VW_FLEET_HGV_PROFILE`), but the `TRAILER_COST_OF_IDLENESS` body and `init.ts` reference the neutral `VW_FLEET_VEHICLE_PROFILE` -> `object does not exist`.
- **Resolution:** Renamed the entity to `FLEET_VEHICLE_PROFILE`. Commit `f1dbf1d`.
- **Recommendation:** A partial neutralization rename left the entity name and its references out of sync. A pack lint that checks every `{schema}.VW_*` reference in a data-model body resolves to a declared entity would catch this.

### F3: `scoped_contract.sql` - COMMENT after EXECUTE AS in a stored proc (BLOCKER)

- **Step:** 4 (packs -> scope-arg contract)
- **Severity:** High
- **What happened:** `_ADD_TRIP_KIND_IF_MISSING` had `LANGUAGE SQL / EXECUTE AS CALLER / COMMENT=...` - COMMENT after EXECUTE AS is invalid (`unexpected 'COMMENT'`). This aborted the packs step, and because the proc creation is the FIRST statement in the file, all the scope-arg + FLEET_APP contract functions after it never ran.
- **Resolution:** Moved COMMENT before EXECUTE AS. Commit `f1dbf1d`.
- **Recommendation:** Snowflake requires clause order `LANGUAGE ... COMMENT ... EXECUTE AS ... AS`. This exact ordering bug recurred in 3 places (F3, F6, and the synapse codegen). Worth a repo-wide grep guard for `EXECUTE AS \w+\s*\n?\s*COMMENT`.

### F4: analytic_layer (step 3.5) created `FLEET_APP.LOCATION` before FLEET_APP existed (ERROR, non-fatal)

- **Step:** 3.5 (analytic layer)
- **Severity:** Medium
- **What happened:** `analytic_layer.sql` does `CREATE SCHEMA FLEET_APP.LOCATION`, but `FLEET_APP` DB is not created until the packs step (4). On a first run this failed with `Database 'FLEET_APP' does not exist`. Non-fatal (best-effort), self-healed on idempotent re-run, but not clean first-time.
- **Resolution:** Added defensive `CREATE DATABASE IF NOT EXISTS FLEET_APP` before the LOCATION schema. Commit `13a2ff6`.
- **Recommendation:** Any step that writes into `FLEET_APP.*` before the packs layer should ensure the DB exists (or the LOCATION block should move into the packs layer).

### F5: `V_FACT_TRIPS_CURRENT` (SELECT *) went stale when TRIP_KIND was added later (ERROR)

- **Step:** 3 (projection views) vs 4 (scoped_contract)
- **Severity:** Medium (latent - only exposed once F3 was fixed so TRIP_KIND actually got added)
- **What happened:** `projection_views.sql` builds `V_FACT_TRIPS_CURRENT AS SELECT t.*` (records N columns). `scoped_contract` (step 4) then `ALTER TABLE FACT_TRIPS ADD COLUMN TRIP_KIND`, leaving the SELECT * view stale (`declared 25 columns, but view query produces 26`). Masked previously because F3 aborted before TRIP_KIND was ever added.
- **Resolution:** Ensure `TRIP_KIND` exists (guarded temp proc) at the top of `projection_views.sql`, before the SELECT * view records its column list; the later scoped_contract add becomes a no-op. Commit `13a2ff6`.
- **Recommendation:** Same class as the documented `V_DIM_FLEET_CURRENT` + DIM_FLEET stamp gotcha in AGENTS.md - any `ALTER TABLE ADD COLUMN` on a base table feeding a `SELECT *` `V_*_CURRENT` view must happen before the view is created (or drop+recreate the view after).

### F6: ROUTING_TOOLS substrate silently aborted the whole install (BLOCKER)

- **Step:** 3 (ROUTING_TOOLS.TOOL_* substrate deploy)
- **Severity:** High
- **What happened:** `deploy-agent.sql`'s final verification `SELECT ... FROM INFORMATION_SCHEMA.PROCEDURES` was unqualified and needs a current database. When the engine is already present (no provisioning to set a DB context), the session had none -> `090105 does not have a current database`. Because the installer runs under `set -euo pipefail` and captured the rc with a bare `snow sql ...; RC=$?`, the non-zero exit aborted the ENTIRE install at step 3 with NO error surfaced (script just returned to the prompt).
- **Resolution:** (1) Qualified the 8 verification selects as `FLEET_INTELLIGENCE.INFORMATION_SCHEMA.PROCEDURES`; (2) changed the install-script rc capture to an `if/else` so a non-zero exit degrades to the intended WARN instead of a `set -e` whole-install abort. Commit `a3f8f12`.
- **Recommendation:** This was the most dangerous bug - a silent whole-install abort with no error. Audit all `cmd; RC=$?` patterns in the installer under `set -e` (they are dead-code rc captures). Also: SQL modules run via `snow sql -f` should never rely on an ambient current database - always fully-qualify or `USE DATABASE` at the top.

### F7: synapse proc codegen emitted COMMENT after EXECUTE AS (BLOCKER)

- **Step:** 5 (synapse tool bundles)
- **Severity:** High
- **What happened:** The vendored synapse `procDDL` template (`fleet_tools/vendor/synapse/dist/build/ddl.js`) emitted `RETURNS OBJECT LANGUAGE JAVASCRIPT EXECUTE AS OWNER / COMMENT=... AS` - COMMENT after EXECUTE AS (`unexpected 'COMMENT'`, same rule as F3). `synapse deploy` for the `user` bundle failed, so no MCP servers were created.
- **Resolution:** Moved COMMENT before EXECUTE AS in the codegen template. The bundles symlink the vendored framework, so all 3 bundles picked up the fix. Commit `13943c9`.
- **Recommendation:** Same clause-order guard as F3. Since there is no `.ts` source for the vendored dist, note in the vendor README that the compiled `dist/build/ddl.js` is the edit surface.

### F8: route_optimization idleness view name not neutralized (ERROR - broke SA app Asset Velocity view)

- **Step:** 4 (packs - data presence probe)
- **Severity:** Medium-High (probe ERROR; SA app Asset Velocity view would 404 the view at runtime)
- **What happened:** The pack entity was `TRAILER_COST_OF_IDLENESS` (-> `VW_TRAILER_COST_OF_IDLENESS`), but every consumer (`app-views.json` 5 Asset Velocity queries, the pack manifest `probe:`, `semantic_views.sql`, `init.ts`) uses the neutral `VW_VEHICLE_COST_OF_IDLENESS`. The pack was the last holdout of the old name.
- **Resolution:** Renamed the entity to `VEHICLE_COST_OF_IDLENESS`, aligned `sv_repoint.sql` + `semantic_views.sql`, regenerated setup.sql. Commit `8a22fe2`.
- **Recommendation:** Finish the "neutralize domain naming" pass in the packs layer (the `IDLE_TRAILERS` intermediate entity remains, though it is internal-only and not app-facing). A CI check that every `manifest.yaml` `probe:` target is actually created by its pack setup.sql would catch this class.
