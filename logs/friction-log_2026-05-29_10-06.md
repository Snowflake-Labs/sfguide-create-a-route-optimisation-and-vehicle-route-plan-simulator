## Friction Points

### F1: `ors_control_app` image tag in YAML did not match `image-versions.env`

- **Step:** 4 (image-version validator)
- **Severity:** High (would have blocked Step 6 `CREATE SERVICE FROM @stage` with `Image not found`)
- **What happened:** `scripts/check_image_versions.sh` printed `MISMATCH: service YAMLs missing ors_control_app:v1.1.71`. The env file declares `ORS_CONTROL_APP_TAG=v1.1.71`, but `services/ors_control_app/ors_control_app_service.yaml` line 6 hard-codes `:v1.1.72`. Someone bumped the YAML tag without updating the env file (or vice versa).
- **Resolution:** Edited `ors_control_app_service.yaml` from `v1.1.72` → `v1.1.71` to match `image-versions.env` (per SKILL.md Step 6 pre-deployment-check rule "update the YAML to match the env file"). Validator then printed `PASSED`.
- **Recommendation:** Add a pre-commit / CI hook that runs `scripts/check_image_versions.sh` and blocks PRs that introduce drift. Or have `deploy.sh` auto-update the YAML from the env file at build time rather than expecting hand-sync. The current rule "edit YAML to match env" is invisible to anyone editing the YAML alone.

### F2: Module 02 references a table that module 03 creates (ordering bug)

- **Step:** 6.1 (SQL modules)
- **Severity:** High (blocks the documented run order)
- **What happened:** `02_routing_functions.sql` defines `CREATE OR REPLACE FUNCTION REGION_FOR_POINT(...)` whose body queries `OPENROUTESERVICE_APP.CORE.REGION_ORS_MAP`. That table is only created in `03_region_management.sql` (line 692). With the SKILL.md-prescribed order (`01, 02, 03, …`), module 02 fails with `002003 (42S02): Object 'OPENROUTESERVICE_APP.CORE.REGION_ORS_MAP' does not exist or not authorized.`
- **Resolution:** Ran the modules in the order `01, 03, 02, 04, 05, 06, 07, 08, 15`. Both 02 and 03 use `CREATE OR REPLACE`, so the reorder is safe and idempotent. All 9 modules then completed cleanly.
- **Recommendation:** Either (a) swap the documented module list in `SKILL.md` Step 6 to `01, 03, 02, 04…` and rename files to reflect the dependency order, or (b) split `REGION_FOR_POINT` out of module 02 into a new module that runs *after* 03 (e.g. `03b_routing_functions_region_dependent.sql`). Option (b) keeps the "lower-numbered module = earlier" invariant.

### F3: Nested `$$` literal inside a `$$`-quoted procedure body (snow CLI parse failure)

- **Step:** 6.1 (module 07_studio_jobs.sql)
- **Severity:** High (blocks Studio job creation)
- **What happened:** `STUDIO_START_JOB` is wrapped in `$$ … $$`. Inside the body, `EXECUTE IMMEDIATE` builds a `FROM SPECIFICATION $$' || :spec_yaml || '$$` string. snow CLI / Snowflake's outer parser sees the inner `'$$'` as a premature close of the outer `$$ … $$`, then fails with `syntax error … unexpected '' || :spec_yaml || ''`.
- **Resolution:** Replaced the two inner `'$$'` literals with `CHR(36) || CHR(36)` so the source no longer contains literal `$$` outside of the procedure-body fences. Module then deployed cleanly.
- **Recommendation:** Codify "never write literal `$$` inside a `$$`-quoted body — use `CHR(36) || CHR(36)`" as a rule in `references/snowflake-scripting-guidelines.md`. Add a `scripts/check_dollar_quotes.sh` linter that counts `$$` occurrences inside each procedure body and warns when count is odd.

### F4: `GENERATION_JOBS` schema drift between loader SQL and `ensureUnifiedTables()`

- **Step:** 7 (seed data loader)
- **Severity:** High (blocks initial seed)
- **What happened:** `datasets/load-seed-data.sql` line 600-617 defines `GENERATION_JOBS` *with* a `PRESET_ID VARCHAR` column. But the table is **also** auto-created by the control-app container's `server/studio/ensure-tables.ts` `ensureUnifiedTables()` on first boot, *without* `PRESET_ID`. Because the loader uses `CREATE TABLE IF NOT EXISTS`, the loader does NOT recreate the table; the subsequent `INSERT INTO GENERATION_JOBS (..., PRESET_ID, ...)` fails with `000904 (42000): invalid identifier 'PRESET_ID'`.
- **Resolution:** Manually ran `ALTER TABLE FLEET_INTELLIGENCE.CORE.GENERATION_JOBS ADD COLUMN IF NOT EXISTS PRESET_ID VARCHAR;` and re-ran the loader (`TRUNCATE` + `COPY INTO … FORCE = TRUE` makes it safely idempotent).
- **Recommendation:** Single source of truth for the `GENERATION_JOBS` schema. Either (a) have `ensureUnifiedTables()` create `PRESET_ID` so the loader's `CREATE TABLE IF NOT EXISTS` is irrelevant, or (b) have the loader unconditionally run `ALTER TABLE … ADD COLUMN IF NOT EXISTS PRESET_ID VARCHAR;` immediately after the `CREATE TABLE IF NOT EXISTS`. Option (a) is preferable because the container is the authoritative writer.

### F5: Trailing `DECLARE … BEGIN … END;` block in `route-optimization/references/seed-data.sql` is split by `snow sql -f`

- **Step:** 8 (route-optimization seed)
- **Severity:** Low (the primary region SanFrancisco seeded fine; only the multi-region backfill loop failed)
- **What happened:** The file ends with a Snowflake Scripting block (`DECLARE c CURSOR FOR …; BEGIN FOR rec IN c DO … END FOR; END;`). `snow sql -f` splits the file on `;` boundaries, so the block fragments and Snowflake reports `syntax error line 5 at position 34 unexpected '<EOF>'.` The primary `SEED_ROUTE_OPTIMIZATION_REGION('SanFrancisco')` call had already succeeded (places=52512, lookup=5, job_template=49) before the script reached the broken block.
- **Resolution:** Tolerated — only the "backfill every other DEPLOYED region" loop failed, and we only have one region. The primary verification (`SELECT … FROM PLACES`) showed all expected rows.
- **Recommendation:** Wrap the trailing block in `EXECUTE IMMEDIATE $$ … $$;` so snow CLI sees a single statement. Same workaround as F3/F6.

### F6: Same `DECLARE … BEGIN … END;` problem in `backload-matching/references/bootstrap.sql` (plus Oracle-style `RAISE STATEMENT_ERROR USING MESSAGE = …`)

- **Step:** 8 (backload-matching bootstrap)
- **Severity:** High (blocked all downstream CREATEs in the same file → entire schema empty)
- **What happened:** Two compounded issues:
  1. The pre-flight `DECLARE … BEGIN … END;` block at lines 122-131 was split by `snow sql -f` (same root cause as F5) and aborted execution mid-file. PROPOSAL_DECISIONS, VW_TRAILERS, VW_INTERNAL_VOLUMES, VW_EXTERNAL_OFFERS were never created.
  2. After wrapping the block in `EXECUTE IMMEDIATE $$ … $$;`, the `RAISE STATEMENT_ERROR USING MESSAGE = '…'` line failed with `syntax error line 9 at position 26 unexpected 'USING'`. This is Oracle PL/SQL syntax; Snowflake Scripting requires `DECLARE my_exc EXCEPTION (-20001, '…'); … RAISE my_exc;`.
- **Resolution:** Patched both: wrapped the block in `EXECUTE IMMEDIATE $$ … $$;` and rewrote the RAISE to use a declared EXCEPTION. Re-ran; all 5 backload objects deployed (CONFIG=1, PROPOSAL_DECISIONS=0, VW_TRAILERS=50, VW_INTERNAL_VOLUMES=120, VW_EXTERNAL_OFFERS=300).
- **Recommendation:**
  1. Wrap every Snowflake Scripting block in skill reference SQL with `EXECUTE IMMEDIATE $$ … $$;` so they survive `snow sql -f`. This is the standard idiom and should be documented in `references/snowflake-scripting-guidelines.md` Section "Multi-statement Scripting blocks in -f files".
  2. Add the Snowflake `EXCEPTION (-code, 'msg'); … RAISE name;` form to the guidelines and explicitly call out that Oracle's `RAISE name USING MESSAGE = …` is **not** supported.

### F7: `SYNTHETIC_DATASETS.UNIFIED.V_DIM_FLEET_CURRENT` is missing after initial container boot

- **Step:** 8 (route-optimization Asset Velocity extension)
- **Severity:** Medium (blocks the optional Asset Velocity views in `route-optimization`)
- **What happened:** `extend-dim-fleet-hgv.sql` reads from `V_DIM_FLEET_CURRENT`, but `SHOW VIEWS IN SCHEMA SYNTHETIC_DATASETS.UNIFIED` showed only 7 of the 8 documented `V_*_CURRENT` views — the FLEET one was missing even though `DIM_FLEET` and `DIM_DATASETS` (active=1) were populated. The script's own first statement `DROP VIEW IF EXISTS V_DIM_FLEET_CURRENT` (per its F4 comment) assumes `init.ts` will re-create the view on the next container start, but in a single-session install you don't restart the container, so the view stays dropped.
- **Resolution:** Manually created `V_DIM_FLEET_CURRENT` with the canonical dataset-scoped pattern (mirroring `V_DIM_POIS_CURRENT` DDL), then re-ran only the trailing `CREATE OR REPLACE VIEW VW_FLEET_HGV_PROFILE` portion. After that, `asset-velocity-views.sql` ran cleanly. The downstream `VW_IDLE_TRAILERS` / `VW_LANE_DEMAND` / `VW_TRAILER_COST_OF_IDLENESS` come up with 0 rows on this default `ebike` seed (expected — they require an HGV preset, as documented in the SKILL.md).
- **Recommendation:**
  1. Make `init.ts` also create `V_DIM_FLEET_CURRENT` on boot (it currently creates the other 7 V_*_CURRENT views — see `AGENTS.md` "DIM_DATASETS bootstrap invariant"). The missing view is almost certainly an init.ts omission.
  2. Update `extend-dim-fleet-hgv.sql` to *recreate* `V_DIM_FLEET_CURRENT` immediately after the `ADD COLUMN` statements (and before the trailing CTAS) instead of relying on a future container restart. The view definition is a 5-line `JOIN DIM_DATASETS WHERE IS_ACTIVE = TRUE`; embedding it locally is cheap and removes the boot-order coupling entirely.
