## Friction Points

### F1: `docker push` of engine images hangs on SPCS manifest commit (token-refresh bug)

- **Step:** Engine 3 (build + push 4 images)
- **Severity:** High
- **What happened:** All 10 layers of `openrouteservice:v9.0.0` uploaded ("Pushed"), but the final manifest PUT never completed - the push process sat idle for 3+ min with no `digest:` line and the registry showed "No data". This is the documented SPCS bearer-token-expiry-mid-PUT bug. `provision_engine.sh`'s `build_push()` has no timeout and no crane fallback, so the orchestrator would have hung indefinitely.
- **Resolution:** Killed the hung push + orchestrator. Logged into the registry, then `docker save <img> -o img.tar && crane push img.tar <repo>/<img>:<tag>` for all 4 images (crane handles token refresh correctly). All 4 committed (ORS 250 MB took ~12 min on a ~5 Mbps uplink). Re-ran the orchestrator with `SKIP_IMAGES=1` to continue from staging.
- **Recommendation:** Add an automatic crane fallback to `build_push()` in `provision_engine.sh`: on `docker push` failure OR a stall (no progress for N seconds), `docker save | crane push`. Detect crane presence in preflight and surface a clear hint if absent. This is already documented in AGENTS.md as a manual workaround - promote it into the script so a clean `--with-engine` run does not hang.

### F2: Runtime auto-detect prefers Podman; user asked for Docker; Podman machine only 2 GB

- **Step:** Engine 3 (runtime selection)
- **Severity:** Medium
- **What happened:** `provision_engine.sh` auto-detects `podman` before `docker` (checks `command -v podman` first). Podman 5.7.1 was installed with a running 2 GB / 2-CPU machine. The first run (no `CONTAINER_CMD`) would have built on Podman, against the explicit "use docker" request and on a far smaller VM than Docker Desktop (12 CPU / 8 GB).
- **Resolution:** Stopped the run and relaunched with `CONTAINER_CMD=docker` exported.
- **Recommendation:** Document `CONTAINER_CMD` prominently in SKILL.md Prerequisites/Configuration (it is only in a script comment today). Optionally warn when the selected Podman machine has < 4 GB RAM, and/or honor a repo/profile default. Consider preferring `docker` when both are present, or prompting.

### F3: `SKIP_DATA=1` skips the DIM_FLEET asset-column stamp + projection views that the packs require

- **Step:** 2 (data) → 4 (packs)
- **Severity:** High
- **What happened:** To shorten a re-run after the crane workaround, I set `SKIP_DATA=1`. But `vehicle_profile_catalog.sql` (which ALTERs `DIM_FLEET` to add `WEIGHT_TONS/HEIGHT_M/LENGTH_M/WIDTH_M/AXLELOAD_T/HAZMAT/VEHICLE_SUBTYPE`) and `projection_views.sql` are intended to run **even on data-reuse** - they live after the seed `if/else` but inside the `SKIP_DATA` guard. Skipping them left `DIM_FLEET` without the asset columns, so the packs step failed creating `F_DIM_FLEET_SCOPED` with `invalid identifier 'F.WEIGHT_TONS'`, aborting the orchestrator at step 4.
- **Resolution:** Re-ran without `SKIP_DATA` (data rows were detected and reused; the catalog stamp + projection views then ran). Packs succeeded on the retry (0 invalid-identifier errors).
- **Recommendation:** Move `vehicle_profile_catalog.sql` + `projection_views.sql` out from under the `SKIP_DATA` guard (they are idempotent and cheap), or gate them on their own `SKIP_PROJECTIONS` flag, or have the packs preflight-check for the asset columns and run the stamp on demand. At minimum, document that `SKIP_DATA=1` is only safe once DIM_FLEET has already been stamped.

### F4: `SKIP_INFRA=1` leaves `COMPUTE_POOL` unbound → admin-app deploy aborts

- **Step:** 8 (deploy apps), `install_fleet_apps.sh:250`
- **Severity:** High
- **What happened:** With `SKIP_INFRA=1`, the infra step (which resolves/exports `COMPUTE_POOL`, `IMAGE_REPO_SQL_NAME`, etc.) was skipped. The FLEET_ADMIN_APP deploy at line 250 references `$COMPUTE_POOL`; under `set -u` this aborted with `line 250: COMPUTE_POOL: unbound variable`. FLEET_SA_APP had already deployed, but the admin app did not.
- **Resolution:** Re-ran with infra NOT skipped (fast detect-and-reuse, which binds the vars) and everything else skipped except apps. Admin app then deployed (v0.1.2) and reached READY.
- **Recommendation:** Always resolve infra variables (the cheap "detect" half) even when `SKIP_INFRA=1` skips the "create" half, OR have the apps step independently resolve `COMPUTE_POOL` (e.g., reuse `OPENROUTESERVICE_APP_COMPUTE_POOL`/`FLEET_APPS_COMPUTE_POOL`). Add `: "${COMPUTE_POOL:?…}"` guards with a helpful message.

### F5: Routing-contract grants target FLEET_APP_USER before the roles step creates it

- **Step:** 3 (routing contract) vs 6 (roles)
- **Severity:** Medium
- **What happened:** The routing contract (step 3) runs `GRANT … ON ROUTING_PLATFORM… TO ROLE FLEET_APP_USER`, but `FLEET_APP_USER` is not created until the roles step (step 6). On a first install the grant fails with `Role 'FLEET_APP_USER' does not exist`, producing the step-3 "routing contract setup reported errors" WARN. Live routing verbs would then be ungranted to the consumer role.
- **Resolution:** After the full run (roles now exist), re-ran the routing contract + roles steps; the `ROUTING_PLATFORM` grants to FLEET_APP_USER applied cleanly with no role-missing errors.
- **Recommendation:** Create the FLEET_APP roles before the routing-contract step (or re-apply the contract's role grants at the end of the roles step). Ordering should guarantee the grant targets exist on a clean install.

### F6: Stale grant - `FLEET_INTELLIGENCE.SEMANTIC` schema does not exist in the agnostic layout

- **Step:** 6 (roles + grants)
- **Severity:** Low
- **What happened:** `role_binding.sql` runs `GRANT SELECT ON ALL SEMANTIC VIEWS IN SCHEMA FLEET_INTELLIGENCE.SEMANTIC TO ROLE FLEET_APP_USER`, but that schema does not exist (the agnostic packs place views under `FLEET_APP.*` - CATCHMENT/CORE/DWELL/FLEET_OPS/ROUTE_DEVIATION/ROUTE_OPTIMIZATION/UNIFIED_FLEET). Produces the step-6 "some grants failed" WARN. Non-fatal; the load-bearing grants (FLEET_INTELLIGENCE + SYNTHETIC_DATASETS usage) succeeded.
- **Resolution:** None needed for this run; noted.
- **Recommendation:** Remove or conditionalize the `FLEET_INTELLIGENCE.SEMANTIC` grant in `role_binding.sql`, or point it at the actual `FLEET_APP.*` schemas where the agnostic semantic objects live.

### F7: Slow stage uploads + cosmetic default-region status (INFO)

- **Step:** 2 (seed parquet, 85 MB) and Engine 4 (PBF, 24 MB)
- **Severity:** Low
- **What happened:** (a) `snow stage copy --recursive` uploads file-by-file with per-file MD5/compress overhead; the 85 MB seed set took several minutes with no progress output (looked stalled). (b) `ROUTING_PLATFORM.CONTRACT.ROUTING_STATUS()` with no region argument reported `ors_host: ors-service-europe`, `service_ready: false` - a default-region (`DEFAULT_REGION_NAME`) mismatch - even though SanFrancisco (the real `IS_DEFAULT=true` region) is fully ready. `ROUTING_STATUS('SanFrancisco')` correctly reports ready.
- **Resolution:** Waited out the uploads (verified progress by listing stage file counts); used region-scoped status calls.
- **Recommendation:** (a) Surface upload progress (or note expected duration) for the recursive stage copies. (b) Align the contract `ROUTING_STATUS()` default region with the seeded/`IS_DEFAULT` region (SanFrancisco) so the no-arg status is not misleading.
