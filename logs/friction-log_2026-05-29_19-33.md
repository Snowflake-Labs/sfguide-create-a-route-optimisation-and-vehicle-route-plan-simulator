## Friction Points

### F1: Background SQL-module run produced no incremental stdout for ~10 min during SF graph build

- **Step:** 6 (Deploy app)
- **Severity:** Low
- **What happened:** `run_sql_module.sh` running in a backgrounded shell showed
  "(no output yet)" on repeated `bash_output` polls while module 03
  (region_management → BOOTSTRAP_DEFAULT_REGION) appeared to hang. It was not
  hung - module 03 only takes ~46 s (it CREATEs the per-region procs and kicks
  off the SF service; the graph build happens asynchronously in the container).
  The stdout buffering of `snow sql -f` piped through the wrapper lags badly, so
  the OK markers all flushed at once near the end. The module chain actually
  finished at 19:08:34 (~2.5 min total) per the F1-fix status log.
- **Resolution:** Switched from tailing the noisy stdout to polling
  `${TMPDIR}/run_sql_module_status.log` (the compact START/OK/FAIL log added by
  the F1 fix) and `SHOW SERVICES` / `ORS_STATUS('SanFrancisco')` directly. That
  immediately confirmed progress and readiness.
- **Recommendation:** Add a one-line note to build-routing-solution Step 6 telling
  the operator to monitor `${TMPDIR:-/tmp}/run_sql_module_status.log` (and
  `ORS_STATUS`) rather than the backgrounded stdout, since `snow sql -f` stdout
  buffers and looks stalled. Consider defaulting the wrapper to `QUIET=1` for the
  module loop so the status log is the primary signal.

### F2: Seed-data telemetry upload threw transient SSL/Timeout retries

- **Step:** 7 (Load seed data - `snow stage copy synthetic_ebikes/`)
- **Severity:** Low
- **What happened:** Three `fact_vehicle_telemetry` parquet PUTs logged
  `SSLError("read error")` / `TimeoutError()` "Retrying..." messages mid-upload.
- **Resolution:** Snow CLI's built-in retry recovered automatically; all files
  ended `UPLOADED`. A subsequent `LIST` + the loader verify (TELEMETRY=518,535)
  confirmed completeness, so no manual re-upload was needed.
- **Recommendation:** Note in Step 7 that transient SSL/timeout retries on the
  large telemetry parquet set are expected and self-healing; the authoritative
  check is the post-load row-count verify, not the absence of retry warnings.

### F3: Seed-data loader's long tail is a 518K-row UPDATE, easily mistaken for a hang

- **Step:** 7 (`datasets/load-seed-data.sql`)
- **Severity:** Low
- **What happened:** The loader ran ~17 min; for most of that it was on a single
  `UPDATE SYNTHETIC_DATASETS.UNIFIED.FACT_VEHICLE_TELEMETRY SET TS = DATEADD(...)`
  re-basing 518K telemetry timestamps to recent dates. With no per-statement
  progress it looks stalled.
- **Resolution:** Confirmed it was live via `QUERY_HISTORY()` (the UPDATE was
  RUNNING), then waited it out; loader completed and verify counts matched.
- **Recommendation:** Add an expected-duration note to Step 7 (~15-20 min,
  dominated by the telemetry timestamp re-base UPDATE) so operators don't
  interrupt it. Optionally split the UPDATE into batched chunks or do the
  re-base inside the COPY transform to avoid a full-table UPDATE pass.

### F4: Route-optimization PLACES is 0 after module 15, populated only by the demo skill

- **Step:** 6 → 8 (module `15_route_optimization_seed.sql` vs route-optimization demo)
- **Severity:** Info
- **What happened:** Module 15 (run during base deploy) creates the
  ROUTE_OPTIMIZATION schema/tables/procs but leaves PLACES=0 - the
  `SEED_ROUTE_OPTIMIZATION_REGION` call at its tail is best-effort and returned
  without inserting on a fresh SF install. This briefly looked like a failure.
  It is expected: the route-optimization demo's `seed-data.sql` is what actually
  populates PLACES (got 52,512).
- **Resolution:** Proceeded to the route-optimization demo, which seeded PLACES
  correctly. No action needed.
- **Recommendation:** Add a sentence to build-routing-solution noting that
  ROUTE_OPTIMIZATION.PLACES is expected to be 0 after module 15 on a fresh
  install and is populated by the route-optimization demo (Step 8), so a 0 count
  there is not a defect.

### F5: Agent tool call signature is easy to misuse (TOOL_DIRECTIONS takes ONE description, not from/to)

- **Step:** 8 (Routing Agent verification)
- **Severity:** Info (self-inflicted during verification)
- **What happened:** First test called
  `TOOL_DIRECTIONS('Union Square...', 'Fisherman Wharf...')` treating it as
  (from, to). The 2nd positional arg is actually `PROFILE`, so the invalid
  "profile" caused ORS error 2003 and only one location geocoded. Re-calling with
  a single natural-language description
  (`'Driving directions from Ferry Building to Golden Gate Park in San Francisco'`)
  returned SUCCESS (11 km / 18.1 min). Raw `OPENROUTESERVICE_APP.CORE.DIRECTIONS`
  table function also verified working directly.
- **Resolution:** Corrected the test call; tool works as designed.
- **Recommendation:** The routing-agent SKILL.md "Sample queries" already use
  single-description phrasing - consider adding an explicit note that the tool
  procs take ONE free-text description (the agent passes the whole user prompt),
  not separate origin/destination args, to prevent manual-test confusion.
