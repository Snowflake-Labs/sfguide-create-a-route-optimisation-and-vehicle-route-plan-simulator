## Friction Points

### F1: TRIP_KIND "ambiguous column name" blocks pack install

- **Step:** 4 (pack install / scoped_contract.sql line 36)
- **Severity:** High
- **What happened:** `ALTER TABLE IF EXISTS SYNTHETIC_DATASETS.UNIFIED.FACT_TRIPS ADD COLUMN IF NOT EXISTS TRIP_KIND VARCHAR(16) DEFAULT 'LADEN'` throws `002028 (42601): SQL compilation error: ambiguous column name 'TRIP_KIND'`. The column already existed (confirmed via DESCRIBE). This is a Snowflake behavior where `ADD COLUMN IF NOT EXISTS` with a DEFAULT value on an existing column produces this misleading error instead of silently succeeding.
- **Resolution:** Manually dropped the column and re-added it to reset the state, then re-ran scoped_contract.sql with the offending line commented out (sed). All subsequent views/functions compiled correctly since the column exists.
- **Recommendation:** Replace the `ALTER TABLE ... ADD COLUMN IF NOT EXISTS TRIP_KIND ...` with a guarded approach:
  ```sql
  -- Guard: only add if not present
  BEGIN
    ALTER TABLE SYNTHETIC_DATASETS.UNIFIED.FACT_TRIPS ADD COLUMN TRIP_KIND VARCHAR(16) DEFAULT 'LADEN';
  EXCEPTION WHEN OTHER THEN NULL;
  END;
  ```
  Or better: query INFORMATION_SCHEMA.COLUMNS first and skip if present. This is a known Snowflake edge case with DEFAULT+IF NOT EXISTS on existing columns.

### F2: ALLOW_DIRTY not set causes app deploy failure on dirty tree

- **Step:** 7 (app deploy)
- **Severity:** Medium
- **What happened:** The deploy_fleet_sa_app.sh script refuses to deploy when there are uncommitted changes in the working tree. On a from-scratch install, this is likely (generated SQL files, node_modules changes, etc.). The error message is clear: "Commit, stash, or set ALLOW_DIRTY=1".
- **Resolution:** Re-ran the installer with `ALLOW_DIRTY=1` env var and SKIP flags for completed layers. Apps deployed successfully.
- **Recommendation:** The main installer script should either: (a) set `ALLOW_DIRTY=1` automatically during a fresh install, (b) warn prominently at preflight that uncommitted changes exist and offer to set ALLOW_DIRTY, or (c) the SKIP_* re-run should not require repeating layer 0-3.4. The current behavior means a from-scratch install that hits this needs two passes unless the user knows to set ALLOW_DIRTY upfront.

### F4: Compute pool STARTING state during module 01 load

- **Step:** 3 (engine SQL module 01_core_infra)
- **Severity:** Low
- **What happened:** The compute pool was in STARTING state when module 01 tried to create services on it. Module 01 prints a WARNING: "Pool state is STARTING. Wait for ACTIVE then re-run 01_core_infra.sql". However the CREATE SERVICE IF NOT EXISTS statements succeeded (services enter a pending state while pool starts). The services eventually came up once the pool reached ACTIVE.
- **Resolution:** No manual intervention needed - the services waited for the pool and started automatically.
- **Recommendation:** The WARNING message in module 01 is misleading for automated runs where the script continues anyway. Consider either: (a) polling until ACTIVE before creating services, or (b) rewording the message to "Pool is STARTING - services will queue until pool is ACTIVE (no re-run needed)."
