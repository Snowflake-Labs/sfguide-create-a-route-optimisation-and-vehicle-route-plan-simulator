## Friction Points

### F1: App deploy failed - service spec image path did not match the resolved image repository (HIGH)

- **Step:** 8 (deploy FLEET_SA_APP / FLEET_ADMIN_APP)
- **Severity:** High (aborted the orchestrator before any app endpoint was produced)
- **What happened:** On a from-scratch `--with-engine` run, step 1 (infra) resolves to the **FLEET-owned** repo (`FLEET_INTELLIGENCE.CORE.IMAGE_REPOSITORY`) because `OPENROUTESERVICE_APP` does not exist yet - it is only created later by the engine step (3). The app deploy scripts push the image to the resolved repo (correct: `…/fleet_intelligence/core/image_repository/fleet_sa_app:v0.1.14`), but the committed service YAMLs hardcode `/openrouteservice_app/core/image_repository/fleet_sa_app:<tag>` and the render step only rewrote the **tag** (`sed … fleet_sa_app:`), never the **repo path**. Result: `CREATE SERVICE … FROM @stage` → `397012: Image …/openrouteservice_app/core/image_repository/fleet_sa_app:v0.1.14 not found.`
- **Resolution:**
  1. Fixed source (new-deployment-first) in `scripts/deploy_fleet_sa_app.sh` and `scripts/deploy_fleet_admin_app.sh`: derive `IMAGE_REPO_PATH` from the resolved `IMAGE_REPO_SQL_NAME` (`lowercase`, `.`→`/`, leading `/`) and add a sed that rewrites the spec's `image:` path prefix to match where the image is actually pushed, in addition to the existing tag rewrite.
  2. Re-ran both deploy scripts with the resolved infra env (`IMAGE_REPO_SQL_NAME=FLEET_INTELLIGENCE.CORE.IMAGE_REPOSITORY`, `COMPUTE_POOL=FLEET_APPS_COMPUTE_POOL`, `CARTO_EAI=FLEET_APP_CARTO_EAI`). SA used `SKIP_IMAGE=1` (image already pushed); admin did a full build. Both services came up RUNNING with endpoints.
- **Recommendation:** Land the deploy-script fix in the repo (commit) so a fresh `--with-engine` install on a clean account no longer fails at step 8. Longer-term, consider making the orchestrator prefer/anticipate the engine repo (`OPENROUTESERVICE_APP.CORE.IMAGE_REPOSITORY`) when `--with-engine` is set, OR strip the hardcoded repo path from the committed service YAMLs entirely and always derive it at render time (the fix already does the latter defensively).

### F2: Role grants warned because SYNAPSE_USER schema is created after the roles step (MEDIUM)

- **Step:** 6 (roles + grants)
- **Severity:** Medium (non-fatal warning, but leaves the app service-role / app-schema grants unapplied until manually re-run)
- **What happened:** `role_binding.sql` grants on `FLEET_INTELLIGENCE.SYNAPSE_USER` (schema, agents, and the `FLEET_SA_APP!ALL_ENDPOINTS_USAGE` service role). That schema and the service are only created in step 8 (apps). On the first pass the grants failed with `Schema 'FLEET_INTELLIGENCE.SYNAPSE_USER' does not exist or not authorized` (logged to `/tmp/ifa_roles.log`), and the orchestrator emitted `WARN: some grants failed`.
- **Resolution:** Re-ran `fleet_sa_app/app/role_binding.sql` after step 8 completed; every grant then executed successfully (including the service-role endpoint grant).
- **Recommendation:** Either (a) move the roles/grants step to run **after** apps (so SYNAPSE_USER + the service exist), or (b) split role_binding into a pre-app portion (role creation + base schema grants) and a post-app portion (service-role + app-schema grants) invoked at the end of step 8, or (c) have the orchestrator automatically re-apply role_binding once after apps deploy. Today the warning requires a manual re-run to be safe.

### F3: Seed-loader prints engine-only-section errors on the agnostic path (LOW)

- **Step:** 2 (data)
- **Severity:** Low (cosmetic / expected; install continues correctly)
- **What happened:** `WARN: canonical loader reported errors (some engine-only sections may not apply); continuing`. The shared canonical loader contains sections that only apply when the full engine namespace exists; on the agnostic data path these emit errors that are intentionally swallowed.
- **Resolution:** None needed - the warning is expected and the orchestrator continues; downstream packs/SVs/agents all resolved.
- **Recommendation:** Consider gating the engine-only loader sections behind an existence check so the agnostic path produces a clean log, avoiding a scary-looking WARN that an operator might misread as a real failure.

### F4: Long, low-signal phases (seed upload + engine module load) with sparse progress output (LOW)

- **Step:** 2 (seed upload) and 3 (engine module load)
- **Severity:** Low (UX only)
- **What happened:** The ~85 MB file-by-file seed upload (~9 min) only printed two lines ("uploading…", then "staged N seed files"), and the engine SQL module load echoed raw module SQL to stdout/tee (so the log is dominated by SQL text), making it hard to tell real progress from echoed source. Determining liveness required side-channel checks (`LIST @…SEED_DATA_STAGE`, `SHOW SERVICES`, `ps aux | grep crane`).
- **Resolution:** Monitored via stage `LIST`, `SHOW SERVICES … --format json`, and process inspection; confirmed steady progress.
- **Recommendation:** Add a periodic heartbeat / running file count during the seed upload, and run the engine SQL modules with reduced echo (or a per-module "loading 03_… done" marker) so the friction/install log shows clean step boundaries instead of thousands of lines of module SQL.
