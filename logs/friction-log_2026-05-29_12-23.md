## Friction Points

### F1: Backgrounded `run_sql_module.sh` completion markers not surfacing in filtered output

- **Step:** 6 (Deploy app)
- **Severity:** Low
- **What happened:** When running the 9 SQL modules in a background shell, the `OK: <module>.sql` and `ALL MODULES DONE` markers did not reliably appear through filtered `bash_output` reads (the wide `SHOW COMPUTE POOLS` table and large procedure bodies dominated the 30k-char buffer). Module 15 in particular appeared to "hang" for a long time when it had actually completed.
- **Resolution:** Verified completion out-of-band by querying Snowflake for the last object each module creates (e.g. `SHOW PROCEDURES LIKE 'SEED_ROUTE_OPTIMIZATION_REGION'`) and confirmed no `MODULE FAILED` was emitted. Re-ran module 15 standalone to get a definitive `OK`.
- **Recommendation:** Have `run_sql_module.sh` emit a compact one-line-per-module status to a separate `logs/` file (e.g. `module-status.log`) so progress can be tailed without the verbose statement echo. Alternatively suppress full statement echo and only print status rows.

### F2: route-optimization `seed-data.sql` trailing "backfill DEPLOYED regions" block raises a syntax error

- **Step:** 8 (Deploy demos → route-optimization)
- **Severity:** Low
- **What happened:** The SanFrancisco seed succeeded (`Seeded for SanFrancisco: places=52512, lookup=5, job_template=49`), but the script's final backfill section (loop over `STATUS='DEPLOYED'` regions) failed with `001003 (42000): SQL compilation error: syntax error line 10 at position 90 unexpected '.'`.
- **Resolution:** Non-blocking — the primary region seed completed; verified `JOB_TEMPLATE`=49 for SanFrancisco. Demo is fully functional.
- **Recommendation:** Fix the dynamic-SQL string in the backfill block of `.cortex/skills/route-optimization/references/seed-data.sql` (likely an unescaped/over-qualified identifier in an `EXECUTE IMMEDIATE`), or guard it so a single-region greenfield install doesn't hit the broken branch.

### F3: dwell-analysis `DT_SLA_ALERTS` = 0 rows on the ebike seed preset

- **Step:** 8 (Deploy demos → dwell-analysis)
- **Severity:** Medium
- **What happened:** All 8 Dynamic Tables created successfully and populated (STATE_CHANGES=518535, DWELL_SESSIONS=11971, DAILY_TRENDS=8), but `DT_SLA_ALERTS`=0 even though `DT_DWELL_ENRICHED` has dwell sessions up to 1439 min vs a 15-min minimum WARNING threshold. The location-type values on the ebike seed sessions do not match the `SLA_THRESHOLDS` location types (WAREHOUSE/DESTINATION/REST_STOP/STORE/DETOUR), so the breach join produces no rows.
- **Resolution:** Left as-is — the skill documents `DT_SLA_ALERTS`=0 as an acceptable seed-data artifact; the pipeline itself is healthy and the page renders. Forced `ALTER DYNAMIC TABLE ... REFRESH` confirmed "No new data" (not a refresh-lag issue).
- **Recommendation:** Either (a) seed `DIM_POIS` location types that map to a threshold type for the SF ebike dataset, or (b) add a default/catch-all threshold row so any dwelling location can breach, or (c) call this out explicitly in the dwell-analysis verification step so the operator isn't surprised by a zero count.

### F4: freight-exchange bootstrap defaults `MARKETPLACE.CONFIG` to `hgv`, leaving the page empty on the active ebike preset

- **Step:** 8 (Deploy demos → freight-exchange)
- **Severity:** Medium
- **What happened:** `bootstrap.sql` created the marketplace objects fine, but `MARKETPLACE.CONFIG` was seeded with `SanFrancisco/hgv` while the loaded seed data (and the rest of the demos) are on `SanFrancisco/ebike`. As a result `VW_OFFERS`/`VW_OFFER_ENRICHED`/`VW_PARTNERS` all returned 0 rows until CONFIG was aligned.
- **Resolution:** `UPDATE FLEET_INTELLIGENCE.MARKETPLACE.CONFIG SET VEHICLE_TYPE='ebike', REGION='SanFrancisco';` → VW_OFFERS=300, VW_OFFER_ENRICHED=300, VW_PARTNERS=80.

The control app auto-syncs CONFIG when the user switches preset, but the initial greenfield value should match the loaded seed so the page shows data immediately.
