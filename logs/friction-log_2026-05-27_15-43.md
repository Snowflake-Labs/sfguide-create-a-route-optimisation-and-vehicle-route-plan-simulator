## Friction Points

### F1 — `02_routing_functions.sql` referenced `REGION_ORS_MAP` before module 03 created it; `run_sql_module.sh` returned RC=0 despite the SQL error
- **Symptom:** During the SQL-modules loop, module 02 emitted `Object 'OPENROUTESERVICE_APP.CORE.REGION_ORS_MAP' does not exist or not authorized.` but the wrapper script printed `OK: 02_routing_functions.sql` and continued. One UDF (`SAMPLE_ADDRESSES_FOR_REGION` etc.) was therefore never created on the first pass.
- **Resolution this run:** Re-ran 02 manually after 03 finished; all functions then compiled.
- **Recommendation:** Either (a) reorder the loop so `03_region_management.sql` (which creates `REGION_ORS_MAP`) runs before `02_routing_functions.sql`, or (b) tighten the `run_sql_module.sh` regex so it catches the boxed `╭─ Error` snow-CLI output, not just `002xxx (4xxxx)` markers. Document a follow-up `02` re-run in `SKILL.md` step 6 as a fallback.

### F2 — `route-optimization/references/seed-data.sql` assumed `FLEET_INTELLIGENCE.ROUTE_OPTIMIZATION` schema and `CONFIG` table already existed
- **Symptom:** First run failed at `CREATE STAGE … ROUTE_OPTIMIZATION.NOTEBOOK` with `Schema 'FLEET_INTELLIGENCE.ROUTE_OPTIMIZATION' does not exist`. After creating the schema, the next pass failed at the `MERGE INTO …CONFIG` because `CONFIG` is created by `15_route_optimization_seed.sql` and not by the seed script itself.
- **Resolution this run:** Created `FLEET_INTELLIGENCE.ROUTE_OPTIMIZATION` manually, then explicitly ran `bash run_sql_module.sh … 15_route_optimization_seed.sql`, then re-ran `seed-data.sql`.
- **Recommendation:** `build-routing-solution/SKILL.md` Step 6 should add `15_route_optimization_seed.sql` to the loop list (it lives in the same `app/modules/` folder but is not in the `for m in …` list). Alternatively make `route-optimization/references/seed-data.sql` self-bootstrap the schema and call `15…` first.

### F3 — `seed-data.sql` ends with a `DECLARE … BEGIN … END;` cursor block that snow CLI splits on `;`
- **Symptom:** The trailing scripted block to backfill every `DEPLOYED` region failed with `syntax error … unexpected '<EOF>'` because snow CLI splits the multi-statement file on `;`.
- **Resolution this run:** Skipped the block and called `CALL FLEET_INTELLIGENCE.ROUTE_OPTIMIZATION.SEED_ROUTE_OPTIMIZATION_REGION('SanFrancisco')` directly via `snowflake_sql_execute`.
- **Recommendation:** Wrap the block in `EXECUTE IMMEDIATE $$ … $$;` so snow CLI treats it as a single statement, or move it to a `.py` notebook step.

### F4 — Control-app `init.ts` failed to create `V_*_CURRENT` views because `FLEET_INTELLIGENCE.CORE.DIM_DATASETS` did not exist

**Status:** FIXED in `ors_control_app:v1.1.58`. `init.ts` now calls `ensureUnifiedTables()` (from `studio/ensure-tables.ts`) before any `V_*_CURRENT` view CREATE, so `DIM_DATASETS` is guaranteed to exist on every boot. `extend-dim-fleet-hgv.sql` now `DROP VIEW IF EXISTS V_DIM_FLEET_CURRENT` before its `ALTER TABLE … ADD COLUMN` block, so the column-drift secondary failure is eliminated. Verified on this account by dropping `DIM_DATASETS` + all 7 `V_*_CURRENT` views and resuming the service: boot recreated everything automatically without manual SQL.
- **Symptom:** After step 6 the control-app booted but `SHOW VIEWS … LIKE 'V_%_CURRENT'` returned 0 rows. Service logs showed `Object 'SYNTHETIC_DATASETS.UNIFIED.V_DIM_PARTNERS_CURRENT' does not exist`. Every demo that joins through these views (asset-velocity-views, freight-exchange enrichment) blocked downstream.
- **Resolution this run:** Manually `CREATE TABLE FLEET_INTELLIGENCE.CORE.DIM_DATASETS` (mirroring `studio/ensure-tables.ts`) and inserted one backfill row, then SUSPEND/RESUME `ORS_CONTROL_APP`. Also had to `DROP VIEW V_DIM_FLEET_CURRENT` after `extend-dim-fleet-hgv.sql` added 7 columns to `DIM_FLEET`, otherwise the next boot of `init.ts` failed with "view declared 13 columns but query produces 20".
- **Recommendation:** The seed loader (`datasets/load-seed-data.sql`) should also create + backfill `DIM_DATASETS` so `init.ts` always finds it. Separately, `extend-dim-fleet-hgv.sql` should `DROP VIEW SYNTHETIC_DATASETS.UNIFIED.V_DIM_FLEET_CURRENT` (or call a Snowflake `EXECUTE AS OWNER` proc on the app side) before altering the underlying table, since adding columns invalidates the existing view definition and silently breaks the next boot.

### F5 — `routing-agent/references/deploy-agent.sql` ends with a verification `SELECT … FROM INFORMATION_SCHEMA.PROCEDURES` that fails when no current database is set
- **Symptom:** Final SELECT raised `090105 (22000): … This session does not have a current database. Call 'USE DATABASE'`. All 7 `TOOL_*` procedures were created correctly; only the verification block errored.
- **Resolution this run:** Verified procedures via `SELECT … FROM FLEET_INTELLIGENCE.INFORMATION_SCHEMA.PROCEDURES` directly. No remediation needed.
- **Recommendation:** Prefix the verification SELECT with `USE DATABASE FLEET_INTELLIGENCE;` or fully-qualify it as `FLEET_INTELLIGENCE.INFORMATION_SCHEMA.PROCEDURES`.

### F6 — `image-versions.env` consistency check flagged 2 doc-only mismatches
- **Symptom:** `scripts/check_image_versions.sh` exited 1 because `references/snowflake-scripting-guidelines.md` lists older tags than `image-versions.env`. One legitimate mismatch (`APP_VERSION="1.1.53"` in the service YAML vs `1.1.55` in env) was a real blocker.
- **Resolution this run:** Edited the YAML to `1.1.55` and proceeded; the doc-only mismatches are non-blocking and were ignored.
- **Recommendation:** Either keep the doc in sync via the `deploy.sh` post-step, or downgrade doc-vs-env mismatches in `check_image_versions.sh` to a WARN (exit 0) and reserve FAIL for actual deployable-artifact mismatches.

### F7 — Control-app build can produce zero stdout in agent-managed terminals after long npm + docker chains
- **Symptom:** During the ors_control_app docker build (the `cd … && cp .dockerignore.prebuilt .dockerignore && docker build … && docker push` chain) the bash tool returned an empty `bash_output` even though the image had been built locally. `docker images` confirmed `ors_control_app:v1.1.55` existed but the push portion of the chain never executed.
- **Resolution this run:** Ran `docker push` manually as a separate bash invocation; it succeeded in <30 sec because all but one layer was already cached.
- **Recommendation:** Split the control-app build, restore-dockerignore, and push into 3 separate bash invocations (or a small shell script with `set -x`) so any one of them can be re-run idempotently if the orchestrator misses output.
