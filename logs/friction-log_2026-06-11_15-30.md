## Friction Points

### F1: MATRIX endpoint snaps more leniently than the optimization/VROOM path

- **Step:** Diagnose
- **Severity:** Medium
- **What happened:** The v1.1.99 routability pre-filter used `MATRIX_TABULAR` to drop unroutable points, but only treated NULL snaps as unroutable. The MATRIX endpoint returned a finite duration and `snapped_distance: 1155m` for a point that the optimization/VROOM path (which enforces the region `maximum_snapping_radius = 1000m`) then rejected with `Could not find routable point within a radius of 1000.0 meters`. So a point can PASS the probe yet ABORT the solve.
- **Resolution:** Applied the solver's 1000m radius as the probe threshold: drop any point whose `snapped_distance > 1000m`. Verified via `_OPTIMIZATION_RAW` that the 1155m point alone reproduces the user's exact error, and excluding it yields a clean `code 0` solve.
- **Recommendation:** Document the MATRIX-vs-routing snap-radius asymmetry in the routing reference. The threshold is hardcoded to 1000m (correct for standard CA/CO/PA regions); for continental-preset regions (`maximum_snapping_radius = 5000m`) a hardcoded 1000m would over-drop valid points. If emergency-response expands to continental regions, make the threshold region-aware (read the per-region snapping radius rather than assuming 1000m).
