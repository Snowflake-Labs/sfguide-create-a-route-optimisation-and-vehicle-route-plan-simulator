## Friction Points

### F1: Canonical loader aborts on `USE WAREHOUSE ROUTING_ANALYTICS` (clean account)

- **Step:** 2 (Data)
- **Severity:** High (BLOCKER on a truly clean account)
- **What happened:** `datasets/load-seed-data.sql`'s first executable statement is `USE WAREHOUSE ROUTING_ANALYTICS`. On a clean account that warehouse does not exist yet (the engine + analytic layer create it, but both run AFTER the data step), so `snow sql -f` aborted immediately and no `SYNTHETIC_DATASETS.UNIFIED.*` tables loaded. Masked in prior installs because ROUTING_ANALYTICS already existed from earlier runs; only a real teardown exposed it.
- **Resolution:** Added `CREATE WAREHOUSE IF NOT EXISTS ROUTING_ANALYTICS` to `scripts/seed_data.sql` (the data-step prep that runs before the loader). Commit `fix(install-fleet-apps): ensure ROUTING_ANALYTICS before the seed loader`.
- **Recommendation:** Keep the data step self-sufficient — never assume engine/analytic-layer objects exist at step 2. (Done.)

### F2: Loader aborts on engine-namespace objects before creating DIM_DATASETS

- **Step:** 2 (Data)
- **Severity:** High (BLOCKER on a truly clean account)
- **What happened:** After F1, the loader still aborted: its first `CREATE TABLE` targets `OPENROUTESERVICE_APP.CORE.INTRO_TRIPS` and it builds `FLEET_INTELLIGENCE.CORE.REGION_REGISTRY_V` which LEFT JOINs `OPENROUTESERVICE_APP.CORE.REGION_CATALOG`. On the agnostic path OPENROUTESERVICE_APP (engine-owned) does not exist at step 2, so those statements fail BEFORE `FLEET_INTELLIGENCE.CORE.DIM_DATASETS` (line 637) — the registry the V_*_CURRENT projection views and every pack depend on.
- **Resolution:** Pre-create `OPENROUTESERVICE_APP` DB + `CORE` schema + an empty `REGION_CATALOG` stub (DDL mirrors engine module 03) in `scripts/seed_data.sql`. The loader then runs through DIM_DATASETS and aborts harmlessly at the engine-only `LOAD_SEED_CATALOG` CALL (after DIM_DATASETS); the orchestrator WARNs and continues. Commit `fix(install-fleet-apps): pre-create OPENROUTESERVICE_APP.CORE + REGION_CATALOG stub`.
- **Recommendation:** Same as F1 — the data step must satisfy the loader's engine-coupled references with idempotent stubs (engine `CREATE IF NOT EXISTS` / `LOAD_SEED_CATALOG` reuse them later). (Done.)

### F3: App deploy clean-tree guard blocked by regenerated synapse `install.json`

- **Step:** 8 (Apps)
- **Severity:** High (BLOCKER for the one-pass install)
- **What happened:** The synapse step (5) regenerates `fleet_tools/_installed/<account>/*/install.json`, which carry a `materializedFrom` git-hash + `materializedAt` timestamp — so they change on every run and dirty the working tree. `deploy_fleet_sa_app.sh`'s clean-tree guard then aborted step 8. The sibling generated files (install.sql/runtime.js/server.js/package.json) were already gitignored; `install.json` was missed.
- **Resolution:** Added `**/_installed/**/install.json` to `.gitignore` and untracked the 4 stale copies. A from-scratch install now reaches the app deploy with a clean tree. Commit `fix(install-fleet-apps): gitignore generated _installed install.json`.
- **Recommendation:** Treat all per-account `_installed/**` artifacts as generated (ignored), never tracked. (Done.)

### F4: `COMPUTE_POOL: unbound variable` when resuming with `SKIP_INFRA=1`

- **Step:** 8 (Apps), re-run path only
- **Severity:** Low (does NOT affect a full one-pass install)
- **What happened:** When resuming only the apps step with `SKIP_INFRA=1`, the orchestrator's admin-app invocation references `$COMPUTE_POOL` (normally set in step 1) under `set -u`, crashing. A full install sets it in step 1, so this never occurs in the primary path.
- **Resolution (this run):** Ran `deploy_fleet_admin_app.sh` directly with `COMPUTE_POOL=FLEET_APPS_COMPUTE_POOL`.
- **Recommendation:** Optional hardening — when any `SKIP_*` is set, resolve infra vars read-only (detect-only) so they are never unbound, or default `COMPUTE_POOL` in the apps step. Deferred (re-run-only, low impact).
