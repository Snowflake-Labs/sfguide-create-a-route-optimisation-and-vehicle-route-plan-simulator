## Friction Points

### F1: step-2 canonical loader calls engine procs that do not exist yet (LOAD_SEED_CATALOG)

- **Step:** 2 data (canonical loader `datasets/load-seed-data.sql`)
- **Severity:** Medium (non-fatal WARN, but violates the zero-WARN bar; also left the region catalog / matrix unseeded at step 2)
- **What happened:** On a fresh `install-fleet-apps` run the data step (step 2)
  runs the canonical loader BEFORE the ORS engine is provisioned (step 3). The
  loader's trailing `CALL OPENROUTESERVICE_APP.CORE.LOAD_SEED_CATALOG(...)`
  aborts with `002141 (42601) Unknown user-defined function ... LOAD_SEED_CATALOG`
  (the proc is only created by engine module `03_region_management`). The
  loader's non-zero exit surfaced as the console WARN
  `"canonical loader reported errors (some engine-only sections may not apply)"`.
  A parallel swallowed error came from `seed_data.sql`'s trailing verification
  `SELECT COUNT(*)` on DIM_DATASETS/FACT_TRIPS, which do not exist on the
  pre-load (seedprep) pass -> `002003 (42S02) Object does not exist`.
- **Resolution:** Fix #1 (commit b34946c5):
  - `datasets/load-seed-data.sql`: wrapped the `CALL LOAD_SEED_CATALOG` in a
    guarded `EXECUTE IMMEDIATE` block with `EXCEPTION WHEN OTHER` so it skips
    silently when the proc is absent (install step 3.4 already re-seeds the
    catalog after the engine loads); the engine-first path still seeds inline.
  - `scripts/seed_data.sql`: wrapped the verification SELECT so each COUNT(*)
    reports -1 for a not-yet-created table instead of erroring.
- **Recommendation:** Any SQL that runs in the data step (before the engine) and
  references engine-namespace procs/objects MUST be guarded (proc-existence
  try/catch) so a fresh install is clean. Consider a lint/check that flags
  ungated `OPENROUTESERVICE_APP.CORE.<proc>(...)` CALLs in files consumed by
  step 2.

### F2: second engine-proc call in the loader was missed by F1 (LOAD_SEED_MATRIX)

- **Step:** 2 data (canonical loader)
- **Severity:** Medium (re-triggered the identical step-2 WARN)
- **What happened:** The loader has a SECOND engine-dependent call,
  `CALL OPENROUTESERVICE_APP.CORE.LOAD_SEED_MATRIX(...)` (created by engine
  module `06_matrix_ops`), which still aborted at step 2 after F1 fixed only
  LOAD_SEED_CATALOG. Same `Unknown user-defined function` -> same console WARN.
  Unlike the catalog, nothing re-seeded the matrix after the engine, so the
  pre-existing flow silently never loaded the seed travel-time matrix at all.
- **Resolution:** Fix #2 (commit de72497a):
  - `datasets/load-seed-data.sql`: guarded the `LOAD_SEED_MATRIX` call the same
    way (skip when absent).
  - `scripts/install_fleet_apps.sh`: added **step 3.4b** to re-seed the
    SanFrancisco cycling-electric RES8 matrix from the baked parquet after the
    engine proc exists (mirrors the 3.4 catalog re-seed), so a fresh install now
    both emits zero WARN AND actually loads the matrix (29,402 rows).
- **Recommendation:** When a loader call is guarded/deferred, always add the
  corresponding post-engine re-seed in the orchestrator (step 3.4/3.4b). Audit
  the loader for ALL engine-proc calls at once rather than one at a time.

### F3: LOAD_SEED_MATRIX references a named file format the engine never creates

- **Step:** 3.4b seed-matrix (newly added)
- **Severity:** Medium (the last remaining WARN)
- **What happened:** With 3.4b calling `LOAD_SEED_MATRIX` post-engine, it failed
  with `002003 File format 'OPENROUTESERVICE_APP.CORE.PARQUET_FF' does not exist
  or not authorized`. The proc body (`06_matrix_ops.sql:317`) hardcodes the
  named file format `OPENROUTESERVICE_APP.CORE.PARQUET_FF` for one MERGE, but no
  engine module creates it. `LOAD_SEED_CATALOG` succeeded because it uses an
  inline `(TYPE = PARQUET)` format. On the retired engine-first path the loader
  itself created `OPENROUTESERVICE_APP.CORE.PARQUET_FF`, but `install-fleet-apps`
  rewrites that reference to the `FLEET_INTELLIGENCE` namespace (sed at
  `install_fleet_apps.sh:177`), so the OPENROUTESERVICE_APP one never existed.
- **Resolution:** Fix #3 (commit 7b2b3a22): added
  `CREATE FILE FORMAT IF NOT EXISTS OPENROUTESERVICE_APP.CORE.PARQUET_FF TYPE=PARQUET`
  (with tracking COMMENT) to engine module `06_matrix_ops.sql`, so the engine
  that owns the proc also owns the file format it references, on every path.
- **Recommendation:** A proc that references a named object (file format, stage)
  should be co-located in a module that creates that object, or use an inline
  format. Grep engine procs for named `*.PARQUET_FF` / stage references that no
  module creates.

### F4: canonical-loader seed parquet upload is slow (INFO)

- **Step:** 2 data
- **Severity:** Low
- **What happened:** The `snow stage copy datasets/ --recursive` uploads 41
  files / ~204 MB file-by-file. The skill text says "~85 MB / a few minutes";
  actual size is ~204 MB and the upload took 3-15 min depending on the run
  (the 8 telemetry parquet files at ~18-21 MB each dominate). Not an error.
- **Resolution:** None needed - waited it out.
- **Recommendation:** Update the step-2 note from "~85 MB" to "~200 MB" so the
  expectation matches reality; optionally tar/zip the seed tree and upload a
  single archive, or use `PUT ... AUTO_COMPRESS=FALSE PARALLEL=n` to speed the
  file-by-file path.

### F5: multi-statement `snow sql -q` halts on first error (INFO, tooling)

- **Step:** wipe (cleanup, not the installer)
- **Severity:** Low
- **What happened:** During teardown, a batched `snow sql -q "stmt1; stmt2; ..."`
  stopped at an `ALTER WAREHOUSE ... SUSPEND` that errored because the warehouse
  was already suspended, leaving the trailing `DROP ROLE`/`DROP WAREHOUSE`
  statements unexecuted.
- **Resolution:** Re-ran the remaining drops individually (skipping the SUSPEND).
- **Recommendation:** In cleanup guidance, drop warehouses directly
  (`DROP WAREHOUSE IF EXISTS` handles a running/suspended WH) rather than
  `ALTER ... SUSPEND` first; or run teardown statements individually.
